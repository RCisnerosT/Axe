> Archetype: Internal Tool (primary) + API/Backend Service (secondary — scanning/alert worker)

## 1. Project Overview

### Vision

A personal swing-trading tool that scans the S&P 500 constituents plus a curated set of liquid, optionable ETFs (SPY, QQQ, IWM, DIA, sector SPDRs, GLD, SLV, TLT, HYG) for **RSI/price divergences** on four timeframes — weekly, daily, 4-hour, and 1-hour. When price and RSI move in opposite directions at a swing pivot inside an extreme RSI zone, the tool flags a divergence, sends an instant Telegram alert, and logs it for later review. A companion dashboard lets the user inspect active divergences, drill into a symbol's chart, and check how the strategy would have performed historically (backtest).

This is a single-user tool. No public users, no billing, no multi-tenant concerns — just speed and correctness for one trader.

### Divergence Definition (core business logic — do not reinterpret)

Comparing two chronologically ordered swing pivots of the same type (both highs or both lows) on the same symbol/timeframe:

- **Bullish divergence**: `price_pivot_1 > price_pivot_2` (price making a lower low) AND `rsi_pivot_1 < rsi_pivot_2` (RSI making a higher low). Only valid when both RSI values are in the **low/oversold zone** (RSI ≤ 40, configurable).
- **Bearish divergence**: `price_pivot_1 < price_pivot_2` (price making a higher high) AND `rsi_pivot_1 > rsi_pivot_2` (RSI making a lower high). Only valid when both RSI values are in the **high/overbought zone** (RSI ≥ 60, configurable).

Where pivot_1 is the earlier point in time and pivot_2 is the more recent one.

### Goals
- Catch swing-trade entries earlier than manually eyeballing 600+ charts across 4 timeframes.
- Zero missed opportunities via instant Telegram alerts.
- Validate the strategy's historical edge via backtest before risking capital.

### Success Metrics
- Alert fires within one scan cycle (≤30 min) of a divergence forming.
- Zero duplicate alerts for the same unresolved divergence.
- Backtest report shows win rate and average return per timeframe/direction.

## 2. Tech Stack

| Layer | Technology | Why |
|-------|-----------|-----|
| Market data | Schwab Trader API (REST + WebSocket) | Free for individual developers with a Schwab account (covers ThinkorSwim); gives price history, option chains (to confirm optionability), and streaming |
| Scanner/backtest language | Python 3.12 | Best ecosystem for numerical work (pandas/numpy); `schwab-py` is the maintained community wrapper for this exact API |
| Schwab API wrapper | `schwab-py` | Handles OAuth token lifecycle and REST/streaming calls; avoids hand-rolling auth |
| RSI implementation | Hand-written Wilder's smoothing (pandas), not a third-party TA library | Wilder's RSI is ~15 lines; avoids depending on `pandas-ta` (known maintenance/ownership issues) for a formula this small |
| Scheduler | GitHub Actions (cron) | Free (public repo: unlimited minutes; private: 2,000 min/mo free), no server to keep alive |
| Database | Supabase (Postgres, free tier) | 500MB free, instant REST API, stays "awake" because the scanner writes multiple times/day |
| Alerts | Telegram Bot API | Free, instant push, trivial setup via BotFather |
| Dashboard framework | Next.js 15 (App Router) + TypeScript | Standard for this archetype, server components read Supabase directly |
| Styling | Tailwind CSS v4 | Fast, consistent with design system below |
| Components | shadcn/ui | Tables, cards, dialogs out of the box |
| Charts | `lightweight-charts` (TradingView, open source) | Only library that does proper candlesticks + indicator subplot + markers well |
| Dashboard data access | Supabase JS client (no ORM) | Read-heavy, simple queries — Prisma/Drizzle would be pure overhead here |
| Dashboard auth | Single-password gate via `iron-session` | One user — a full auth provider (Clerk/NextAuth) is over-engineering |
| Hosting (dashboard) | Vercel (free/Hobby) | Zero-config Next.js hosting |
| Package Manager | pnpm (dashboard) / pip + requirements.txt (scanner) | Standard for each ecosystem |

**No conflicts**: Python (scanner) and TypeScript (dashboard) never talk to each other directly — they're decoupled through Supabase Postgres, which both `supabase-py` and the Supabase JS client support natively. This is the cleanest way to mix a numerics-heavy backend with a JS frontend.

### Relationships
`symbols` 1→N `price_bars`, 1→N `pivots`, 1→N `divergences`, 1→N `backtest_results`. `divergences` references two `pivots` rows. `oauth_tokens` is a standalone singleton.

### Database Schema
```sql
create type timeframe_t as enum ('1h', '4h', '1d', '1w');
create type pivot_kind_t as enum ('high', 'low');
create type direction_t as enum ('bullish', 'bearish');
create type divergence_status_t as enum ('active', 'invalidated', 'expired');
create type exit_reason_t as enum ('opposite_signal', 'horizon', 'still_open');

create table symbols (
  ticker text primary key,
  name text not null,
  type text not null check (type in ('stock','etf')),
  in_sp500 boolean not null default false,
  has_options boolean not null default false,
  active boolean not null default true,
  updated_at timestamptz not null default now()
);

create table price_bars (
  id bigserial primary key,
  ticker text not null references symbols(ticker),
  timeframe timeframe_t not null,
  ts timestamptz not null,
  open numeric not null,
  high numeric not null,
  low numeric not null,
  close numeric not null,
  volume bigint not null,
  rsi numeric,
  unique (ticker, timeframe, ts)
);

create table pivots (
  id bigserial primary key,
  ticker text not null references symbols(ticker),
  timeframe timeframe_t not null,
  ts timestamptz not null,
  kind pivot_kind_t not null,
  price_value numeric not null,
  rsi_value numeric not null,
  confirmed_at timestamptz not null
);

create table divergences (
  id bigserial primary key,
  ticker text not null references symbols(ticker),
  timeframe timeframe_t not null,
  direction direction_t not null,
  pivot_1_id bigint not null references pivots(id),
  pivot_2_id bigint not null references pivots(id),
  detected_at timestamptz not null default now(),
  price_at_signal numeric not null,
  status divergence_status_t not null default 'active',
  alerted_at timestamptz
);

create table backtest_results (
  id bigserial primary key,
  ticker text not null references symbols(ticker),
  timeframe timeframe_t not null,
  direction direction_t not null,
  entry_ts timestamptz not null,
  entry_price numeric not null,
  exit_ts timestamptz,
  exit_price numeric,
  exit_reason exit_reason_t not null default 'still_open',
  return_pct numeric
);

create table oauth_tokens (
  id int primary key default 1,
  access_token text not null,
  refresh_token text not null,
  expires_at timestamptz not null,
  updated_at timestamptz not null default now(),
  constraint single_row check (id = 1)
);
```

## 5. API Design

This project is read-heavy and has no public API consumers — the dashboard talks to Supabase directly from Server Components using the anon (read-only) key. Only one route handler exists:

### Routes Overview
| Method | Path | Description | Auth |
|--------|------|-------------|------|
| POST | `/api/login` | Checks password against `DASHBOARD_PASSWORD`, sets `iron-session` cookie | none (this IS the auth) |

### Key Endpoint Detail

**POST /api/login**
- Request: `{ password: string }`
- On match: sets encrypted session cookie, returns `{ success: true }`
- On mismatch: `401 { success: false }`
- Rate-limit: max 5 attempts per 10 minutes per IP (in-memory counter is fine — single user, low stakes, but stops brute force)

All other data access: Server Components call `supabase.from('divergences').select(...)` etc. directly, protected by `middleware.ts` checking the session cookie before rendering any `(dashboard)` route.

## 8. Authentication & Authorization

### Auth Flow
Single shared password (env var `DASHBOARD_PASSWORD`, stored as a bcrypt hash) → `/login` form → `POST /api/login` → `iron-session` sets an encrypted, httpOnly cookie → `middleware.ts` allows access to `(dashboard)/*`.

### Protected Routes
Everything under `(dashboard)/*` requires a valid session. `/login` and `/api/login` are public.

### Roles & Permissions
Single role: owner. No multi-user, no roles table needed for v1.

### Session Management
`iron-session` encrypted cookie, 30-day expiry, `SESSION_SECRET` env var (32+ random chars). No refresh mechanism needed — re-login after expiry is fine for a personal tool.

## 9. Build Order

**Step 1: Schwab Developer App + Initial OAuth**
Register an app at developer.schwab.com, get `SCHWAB_APP_KEY`/`SCHWAB_APP_SECRET`. Run `schwab-py`'s interactive OAuth helper once locally to obtain the first refresh token. Save it manually into the `oauth_tokens` table (one-time bootstrap — after this, the scanner rotates it automatically).

**Step 2: Supabase Project + Schema**
Create Supabase project, run `supabase/schema.sql` (Section 4) via the SQL editor. Grab the project URL, anon key, and service role key.

**Step 3: Universe Module (`scanner/universe.py`)**
Scrape the Wikipedia "List of S&P 500 companies" table for tickers. Merge with the curated ETF list in `config.py` (SPY, QQQ, IWM, DIA, XLF, XLK, XLE, XLV, XLI, XLY, XLP, XLB, XLU, XLC, GLD, SLV, TLT, HYG). For each symbol, call the Schwab option chain endpoint to set `has_options`. Upsert into `symbols`.

**Step 4: Schwab Client Wrapper (`scanner/schwab_client.py`)**
Wrap `schwab-py`: on each run, load the current token from `oauth_tokens`, refresh if near expiry, save the new token back to Supabase immediately (never leave a stale refresh token in the DB).

**Step 5: Data Ingestion + RSI**
Fetch native 30-minute bars (up to Schwab's ~6-month intraday window) and native daily bars (multi-year history) per active symbol — Schwab's price history endpoint has no native 60-minute frequency, so 1h must be built, not requested directly. Resample 30-min → 1h aligned to the 9:30 ET session open. Resample 1h → 4h, same alignment (4h boundaries fall at 9:30/13:30 ET, never a naive calendar-hour grid). Daily bars need no resampling — they're the 4th scanned timeframe on their own. Resample daily → weekly, grouped by trading week (Monday open to the week's last trading day close). Compute Wilder's RSI(14) on all four series (`indicators.py`). Upsert into `price_bars`.

**Step 6: Pivot + Divergence Detection**
Implement fractal pivot detection (`pivots.py`): a bar is a confirmed high/low pivot if it's the extreme point among itself + N bars before/after. Use N=2 (5-bar fractal) uniformly across all four timeframes (1h, 4h, 1d, 1w) — daily/weekly now have enough native history from Schwab to support the same window without special-casing. Implement `divergence.py` applying the exact definition from Section 1, only within the configured RSI zones. Write new pivots/divergences; mark superseded ones `invalidated`.

**Step 7: Telegram Alerts**
Create a bot via BotFather, get `TELEGRAM_BOT_TOKEN` and your `TELEGRAM_CHAT_ID`. `telegram.py` sends a message only for divergences with `status='active' AND alerted_at IS NULL`, then sets `alerted_at`.

**Step 8: Wire `scan.py` + Local Test Run**
Compose Steps 4-7 into one entry point. Run locally end-to-end against a handful of symbols before scheduling.

**Step 9: GitHub Actions Scheduling**
`.github/workflows/scan.yml`: cron `*/15 13-20 * * 1-5` (UTC, covers 9:30am-4pm ET), checkout, install `requirements.txt`, run `python scanner/scan.py`, secrets from GitHub Actions Secrets (Schwab keys, Supabase service key, Telegram token — `oauth_tokens` table handles the rotating refresh token, not GitHub secrets).

**Step 10: Backtest Engine**
`backtest.py`: for each symbol/timeframe, replay historical confirmed divergences chronologically. Entry at the confirming bar's close. Exit at whichever comes first: an opposite-direction divergence on the same symbol/timeframe, or a fixed horizon (8 bars weekly, 15 bars daily, 20 bars 4h, 40 bars 1h). Compute `return_pct`, persist to `backtest_results`. Schedule via `backtest.yml` (weekly cron + manual `workflow_dispatch`).

**Step 11: Next.js Scaffolding**
`create-next-app` with TypeScript, Tailwind v4, App Router. Install shadcn/ui, `lightweight-charts`, `iron-session`, `@supabase/supabase-js`.

**Step 12: Auth + Middleware**
Build `/login`, `/api/login`, `iron-session` config, `middleware.ts` guarding `(dashboard)/*`.

**Step 13: Dashboard Home**
`DivergenceTable` server component querying active divergences from Supabase, `FilterBar` for timeframe/direction/symbol, animated row entry, `LiveDot` showing last scan time.

**Step 14: Symbol Detail + Charts**
`SymbolChart` wrapping `lightweight-charts`: candlesticks + RSI pane, plot pivot markers and shaded divergence zones. Timeframe tabs: 1w / 1d / 4h / 1h.

**Step 15: Backtest Page + Deploy**
`BacktestStats` (win rate, avg return, counts) + signal log table. Deploy dashboard to Vercel, set env vars (`SUPABASE_URL`, `SUPABASE_ANON_KEY`, `DASHBOARD_PASSWORD` hash, `SESSION_SECRET`). Final polish: loading/empty states, verify dark theme, verify animations aren't excessive.

## 12. Deployment Strategy

### Hosting
- **Scanner**: no hosting — runs entirely inside GitHub Actions on a schedule. Zero servers to maintain.
- **Dashboard**: Vercel free/Hobby tier, connected to the GitHub repo for auto-deploy on push.
- **Database**: Supabase free tier (already provisioned in Step 2).

### CI/CD
`scan.yml` and `backtest.yml` run on schedule via GitHub Actions (Step 9-10). Pushing to `main` auto-deploys the dashboard via Vercel's GitHub integration — no separate CI needed for the frontend beyond Vercel's built-in build step.

### Domain & DNS
Default `*.vercel.app` subdomain is sufficient for a personal tool. Custom domain optional, not required for v1.

### Environments
Single environment (production) — no staging needed for a single-user internal tool. Test scanner changes locally before merging to `main` (which triggers the scheduled workflows to pick up new code on their next run).

## 13. Testing Strategy

### Unit Tests (scanner — pytest)
- `test_indicators.py`: RSI(14) output against known reference values (e.g. a fixed price series with a published expected RSI).
- `test_pivots.py`: fractal detection on synthetic series — confirm pivots only register after N confirming bars, edge cases at series boundaries.
- `test_divergence.py`: table-driven tests directly from the Section 1 definition — bullish case, bearish case, cases that should NOT trigger (RSI outside the extreme zone, wrong price/RSI direction combination).

### Integration Tests
- Run `scan.py` against a small mocked/fixture set of bars (no live API calls) end-to-end: ingestion → RSI → pivots → divergence → Telegram dispatch (mocked) → DB writes (against a local/test Supabase schema or a transactional rollback).

### E2E Tests (dashboard)
Not critical for a single-user internal tool — skip Playwright for v1. If added later, cover: login flow, divergence table renders, symbol chart loads.

## 16. Reglas No Negociables

1. **RSI must be Wilder's smoothing**, hand-written in `indicators.py` — not a third-party TA library. It must match the values the user already sees on ThinkorSwim/TradingView, or alerts won't make sense against his own charts.
2. **1h and 4h bars are built by resampling finer native bars (30-min → 1h → 4h), always aligned to the 9:30 ET session open.** Naive calendar-hour resampling (e.g. midnight UTC buckets) produces wrong candle boundaries and wrong divergence timing. Daily bars are native (no resampling); weekly bars are resampled from daily, grouped by trading week.
3. **The Schwab refresh token is never static.** It expires in 7 days — it must be read from and rewritten to `oauth_tokens` on every single scanner run, never hardcoded or left in a GitHub Actions secret untouched.
4. **No duplicate alerts.** A divergence with `status='active'` and `alerted_at` already set must never trigger a second Telegram message. Only a fresh divergence (new row) or a re-activation after `invalidated` should alert.
5. **1h/4h backtests are capped by Schwab's ~6-month intraday data window** (they're built from 30-min bars, which are intraday). Daily and weekly backtests can go back years since they're built from native daily bars. Don't present backtest results as longer-horizon than the data actually allows — surface the actual date range covered in the UI for each timeframe.
6. **Never over-build the dashboard.** Single user, no roles, no CRUD beyond what's specified. Function over decoration — the animations in Section 7 are the ceiling, not a starting point for more.
